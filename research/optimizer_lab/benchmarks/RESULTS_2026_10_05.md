# GH200 CPU-memory lookup table: measured feasibility

Date: 2026-10-05. **This is not a #92 training reproduction.**

## Verdict

The full 129.95 GB table fits in CPU DRAM, and a carefully implemented table
subsystem runs fast enough to justify attempting the full single-GPU port. We
measured about **6-10.5 ms per global step** of amortized table work. This is an
absolute component cost, not the incremental slowdown of a complete trainer.

## Final measurements

Each independent process allocates and zero-touches the entire table. CPU placement
is enforced and checked; none of its pages reside in GPU HBM. Each stage has 36
different real FineWeb token windows, 6 warmup cycles and 30 measured cycles. A cycle
covers 2 or 4 logical global updates according to the representative stage cadence.
No Transformer computation is overlapped with the measured service.

| Stage | Tokens/global step | Steps/table event | Run A: ms/step | Run B: ms/step | Larger p95 cycle / period: ms |
|---|---:|---:|---:|---:|---:|
| early | 131,072 | 2 | 9.28 | 9.24 | 9.42 |
| middle | 262,144 | 4 | 8.44 | 8.45 | 8.53 |
| late | 393,216 | 4 | 10.48 | 10.47 | 10.63 |
| taper | 327,680 | 4 | 9.52 | 9.50 | 9.70 |
| extension | 131,072 | 4 | 6.10 | 6.11 | 6.16 |

The p95 column is the measured cycle p95 divided by the update period, **not** a
measured full-training-step latency percentile. Event steps incur the cycle cost;
the other steps reuse cached rows. Peak live GPU benchmark tensors reached about
21.25 GiB; the Transformer is not included in that memory figure. The allocator's
reserved peak is reported separately in JSON.

A rough stage-weighted extrapolation gives **11.24 / 11.23 seconds** of
this component over a 1,194-step schedule. This is NOT a total training ETA. It
assumes these representative traces/cadences remain representative; it approximates
the short cadence transition near the beginning of the middle stage.

## What ran

```text
Pinned token upload
  -> GPU hash + unique rows + inverse lookup map
  -> full CPU-resident table/state fetch into HBM cache
  -> synthetic per-occurrence gradient aggregation
  -> unmodified upstream sparse row-Adam kernel
  -> updated weights/state written back to CPU DRAM
  -> synchronize
```

The gradient merge uses FP32 accumulation followed by FP16 storage. It measures a
real aggregation cost but does NOT reproduce the official eight-rank reduction
rounding. Gradients were generated outside timing to stand in for backward output.
The dense model, attention, actual autograd embedding scatter, sampled-softmax
objective, disk/CPU staging and final validation were not executed.

## Correctness and engineering checks

- Tiny offloaded/cache updates match the upstream GPU-only update **bit-for-bit**
  for weights, row second moments and timestamps at events 1, 2, 7, 8 and 100.
  The fixture includes changing row sets, missing-event decay, a beta transition,
  zero gradients and untouched rows. This does not test all of #92's math.
- GPU token hashes match upstream CPU hashes bit-for-bit, including its boundary
  conventions. The inverse map reconstructs the occurrence IDs exactly.
- The FP32 aggregation surrogate agrees with a PyTorch reference within tolerance.
- The full-size stage uses 64-bit flattened indices, exceeding 2^31 elements safely.
- CPU NUMA binding is reapplied after CUDA registration and verified after every
  stage, avoiding the misleading case where nominal host pages occupy GPU memory.
- Dynamic unique-row counts no longer specialize the Triton transfer kernels.
  An earlier version compiled on fresh counts and introduced 100+ ms stalls; those
  intermediate timings are not used for the steady-state result above.

A naive CPU hash/dedup planner was a separate bottleneck (~75-360 ms amortized per
step in the diagnostic). GPU hashing/unique/inverse planning measured about
0.1 ms/step on cached input buffers in its standalone test. Actual CPU data-loader
integration is still outstanding.

## What this establishes / does not establish

**Established:** capacity, host-only placement, small-fixture update equivalence,
and practical measured throughput for the memory/optimizer service on one GH200.

**Not established:** full #92 compatibility, final loss/statistical parity,
optimizer-ranking preservation, complete training wall clock, or 8xH100 performance.
A full port still needs exact source pinning, per-rank sampled-softmax/RNG/FP8
semantics, microbatch accumulation and end-to-end validation. The host uses driver
570 / CUDA 12.8; attention-kernel compatibility must also be addressed for #92.

The result supports **proceeding to a faithful one-GH200 port**, not claiming that
port already exists. All failed/intermediate diagnostics were retained locally.
